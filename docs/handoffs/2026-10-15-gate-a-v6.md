## 1. R8 — report bound to the current review packet

HMA puts a fresh random `review_nonce` (128-bit) and the `review_dispatch_id` in each review packet it
generates. The report contract for HMA reviews requires the report JSON to contain `packet_sha256`,
`review_dispatch_id`, and `review_nonce` equal to the packet's values. Import refuses when any differs.
mtime is no longer used. A previous report, rewritten or not, carries an earlier nonce and is refused. A
completed reviewer that produced no matching report imports nothing: findings stay open, criterion credit
stays zero. Under T, the nonce proves the report was produced from this packet, not that the reviewer
reasoned well.

## 2. R4 — validity boundaries

Validity is the half-open interval `[valid_from, valid_until)`. Revocation (rewind, terminal outcome, policy
change, lease wall-time) sets `valid_until` to the revoking event's time. Launch time `t` = ledger
`started_at`. Authorized only if `valid_from <= t < valid_until`. Equal to `valid_until` → unauthorized.
Equal to a revoking event time → unauthorized (conservative). Ledger and HMA timestamps use the same host
clock at second or finer resolution; ties resolve to unauthorized.

## 3. R7 — final-slot replay

Replay of an existing reservation (same key, same request digest) returns the same record and never charges
again. It returns `launch_eligible: true` only when all hold: the lease is still active by time, stage,
policy, and contract (capacity is **not** rechecked — the slot is already charged); and no ledger run with that
`dispatch_run_id` exists yet. Otherwise `launch_eligible: false`. A new reservation ID needs capacity. So a lost
response on the last slot recovers exactly one launch; a used, expired, or revoked reservation starts nothing.

## 4. R10 — complete reconciliation invariants (supersedes v5 §2 list and v3/v4 matrix rows on
journal/reservation equality)

At import, all must hold, else `UNAUTHORIZED_DISPATCH` (BLOCK):

1. Every ledger run in the declared namespace since the run's first core record matches exactly one
   reservation or one review dispatch, and its `t` is inside that record's validity (§2).
2. Each reservation and each review dispatch matches **at most one** ledger run (no reuse).
3. Reservations with no ledger run stay charged and are listed as `unlaunched` in the scorecard.
4. For HMA-bound verify-loop runs: journal envelope digest == `loop_admission` envelope digest; journal
   controller run ID, live root, clone baseline digest, and ledger namespace == the admission's values.
5. Every journal attempt with a `dispatch_run_id` has a reservation with that ID.
