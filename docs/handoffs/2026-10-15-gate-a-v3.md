## 2. Authority model

### 2.1 Acceptance contract (one additive approval field — D1)

Unchanged from v2 §2.2, with route/permission ceilings added to the contract fields. `ApprovalBinding`
gains one optional field, `acceptance_contract_digest`, omitted when empty (2026-09-08 precedent; existing
digests unchanged). Required on `ACCEPTANCE_CRITERIA -> PLANNING` when a run uses a contract; carried by
every later approval of that run; a mismatch refuses the transition. v2's `execution_lease_digest` is
dropped.

### 2.2 Lease = approved plan unit

- Plan format `hma.plan/v1` (canonical JSON): the §10 unit fields, plus `max_wall_minutes` and declared
  cost ceiling per unit. Its digest is the existing `accepted_plan_digest`.
- Issuance: the unit's latest applicable approved `ROUTE_SELECTION -> IMPLEMENTATION_AUTHORIZATION`
  transition. The host presents the plan document; HMA recomputes its digest and requires equality with
  that approval's `accepted_plan_digest` and that the unit exists in it. A host-written lease record only
  caches this derivation (`lease_digest` = digest of {approval transition digest, unit, plan digest}); it
  grants nothing by itself.
- Active only while: core run not terminal; the unit's projected stage is `IMPLEMENTATION_AUTHORIZATION`;
  no later approved rewind of the unit, the run, or a dependency (§2.3); wall time since approval below
  `max_wall_minutes`; per-unit counters below ceilings; current policy digest equals the approval's
  bound policy; contract digest matches.
- Inside an active lease the host may run implementation→test→fix iterations and record per-change
  independent reviews without new human approvals. Moving to `IMPLEMENTATION_REVIEW` is a normal human
  transition. A review or audit finding that requires going back needs the normal human-approved rewind;
  that rewind's approval issues a fresh lease with counters carried forward (§3.2).
- Walk-through (closure criterion R1): route approval → 0 launches before it (hook refuses: no approval) →
  attempts 1..n allowed in `IMPLEMENTATION_AUTHORIZATION` → human approves `IMPLEMENTATION_REVIEW` →
  hook refuses (stage) → human approves rewind to `IMPLEMENTATION_AUTHORIZATION` → attempts resume with
  carried counters. `ValidStage`/`IsLegalEdge` negative controls retained.

### 2.3 Dependent invalidation

The plan's `dependencies on prior units` (§10) define the graph. A rewind of unit U voids leases of U and
every unit that transitively depends on U. The rule is computed from the approved plan, not from a
submitted list. If the plan document cannot be presented or does not validate, all leases in the run are
void (fail closed). Pre-existing runs without a `hma.plan/v1` document cannot obtain a lease.

## 3. Execution and verify-loop bridge

### 3.1 Routes and escalation

- A lease covers only the unit's approved implementer route (exact profile/provider/model/effort/access
  service, compared against host preflight telemetry). Same-route retries and corrections follow §17:
  one identical retry for `TRANSIENT_RUNTIME_FAILURE`, one bounded correction for
  `CORRECTABLE_EXECUTION_FAILURE`. Same material failure twice → stop, route `FAILED`.
- Any other route — including the plan's `proposed escalation route` — needs human confirmation of the
  §17 classification and a new approved transition. The hook refuses a different route.
- HMA-bound verify-loop envelopes must set `escalate_to: "stop"`; the hook refuses envelopes that do not.

### 3.2 Reservation protocol (`hma host attempt`)

Before each worker launch the controller calls the hook with: controller `run_id`, attempt index,
pre-allocated `dispatch_run_id`, envelope digest, exact route JSON, last failure signature (if any).

1. Under the host per-run lock (from the H3 fix), HMA loads core + host chains, checks the lease
   (§2.2), route equality (§3.1), failure-signature rule (same signature twice → refuse), and
   remaining counters.
2. If a reservation with the same (`run_id`, attempt, `dispatch_run_id`) exists, return it unchanged
   (idempotent; no second count). Otherwise append one `reservation` record and count it immediately.
3. A reservation counts whether or not launch happens; an unknown launch stays counted (conservative).
4. After the worker ends, the controller may call `hma host attempt-result` with the ledger receipt
   digest; this adds evidence, not authority.
5. Counters are per unit and monotonic for the run. A new lease (after an approved rewind) has ceilings
   as totals; spent attempts are never reset.
6. Two controllers racing for the last attempt: the lock serializes; the second is refused.

Mandatory hook: at evidence import HMA reads the verify-loop journal. Any `dispatch_run_id` without a
matching reservation, or an envelope without `authority_hook`, makes the import fail and records a BLOCK
kernel finding (unauthorized dispatch). Envelope ceilings must be ≤ remaining counters.

Evidence: after transfer, HMA re-captures each contract check through its own no-shell capture bound to
head/diff/worktree (N2 fix makes capture verify Git content). The journal digest is implementer
evidence only.

## 4. Findings and audit import

### 4.1 Disposition (§9)

Severity never sets disposition. Rules:
- Kernel (§7.1) violation with reproduction → `BLOCK` (unwaivable; human downgrade refused as today).
- Evidence that a contract criterion's check fails → no new finding class; the criterion is not credited
  (`FAILED`/not verified). Closure is blocked through the criterion, not through an invented blocker.
- Measurable plan complexity-budget exceedance → `WAIVABLE` (§7.2).
- Everything else, any severity → `ADVISORY`.
- A claimed criterion link must name a criterion ID in the contract and include a reproducible check;
  HMA re-runs it. A fabricated or non-reproducing link is recorded as `ADVISORY`.

### 4.2 Snapshot semantics

Core `finding` records gain an additive `findings_snapshot: true` flag (omitted when false). With the
flag, the record's `Findings` list replaces the previous snapshot even when empty. Without it, current
behavior is unchanged (records with no findings do not change state). An empty snapshot is accepted only
from an import bound to an independent review of the exact current target (§4.3).

### 4.3 Review import

| Report verdict | Host review result |
|---|---|
| pass | APPROVE (if provenance checks pass) |
| fix-required | REQUEST_CHANGES |
| blocked / unknown | no approval; next action `ESCALATE_TO_HUMAN` |

Provenance: the import binds the `agent-dispatch` receipt (run ID, agent, model, effort, account home)
digest; HMA checks the receipt exists in the ledger and its model/provider meets §5 independence. Isolation
`partial`/`compromised` is refused for final independent acceptance. Criterion credit: a criterion is
independently verified only if (a) HMA re-captured its check at the bound target and it passed, and (b) an
independent review at that target lists the criterion as verified.
