## Blocking for implementation

These three stop work at the start of implementation, because the deterministic engine cannot be written against them as stated.

### 1. Terminal-outcome derivation is circular

References: `:126-132`, `:450`

`PARTIAL` is defined at `:126-129`. Then `:131` states that `FAILED`, `BLOCKED`, `UNKNOWN`, and `ABORTED` "are derived from the corresponding terminal condition" - which names nothing. Section 17 defines `FAILED` only at route level (`:450`, "ends that route as `FAILED`"), not run level.

A run that stops with three of five criteria passed, one `PERMISSION_OR_SAFETY_BLOCK`, and one `UNKNOWN_FAILURE` is simultaneously `PARTIAL`, `BLOCKED`, and `UNKNOWN` under the current text. Nothing selects between them.

This is blocking because Section 24.1 requires a deterministic engine fixture proving HMA "represents `FAILED`, `BLOCKED`, `UNKNOWN`, `PARTIAL`, and `ABORTED` honestly." That fixture cannot be written without a total ordering.

Required correction: state an explicit precedence function with one predicate per outcome - for example `ABORTED` > `BLOCKED` > `UNKNOWN` > `FAILED` > `PARTIAL` > `VERIFIED_WITH_WAIVERS` > `VERIFIED_SUCCESS` - and define the exact condition that makes each predicate true.

### 2. The approval-binding contract contradicts itself

References: `:164-182`

`:164` states every approval is "universally bound to" a thirteen-field list. That list includes accepted plan digest (`:173`), plan-declared required evidence digest set (`:174`), and active waiver-operation digest set (`:175`). None of those exist at the Grounding to Acceptance criteria transition.

`:179-181` patches exactly one case, exempting produced head and diff for early transitions. `:182` then changes doctrine without saying so: "A packet becomes stale only when a field it actually binds changes."

Which fields a given stage actually binds is never stated anywhere in the document. Section 21 requires CI to "reject approvals made stale by later changes," which CI cannot do without that mapping.

Required correction: replace the universal list with a per-stage binding matrix - rows are the nine stage transitions, columns are the binding fields, cells are bound or not bound. CI and the local gate both read that one table.

### 3. "No unlisted edge is legal" is violated by its own table

References: `:145-159`

`:159` states "No unlisted edge is legal." The invalidation-effect column of the same table requires transitions the From/Target columns never enumerate:

- `:148` - a criteria or non-goal change "rewinds to Acceptance criteria." No row permits Planning, Route selection, Implementation authorization, Implementation review, Verification, or Independent validation to reach Acceptance criteria. Only `:156` (Release and closure) and `:157` (which allows Grounding, Planning, or terminal only) offer rewind targets.
- `:153` - a produced head or diff change "returns to Implementation authorization or review." There is no Verification to Implementation authorization edge and no Verification to Implementation review edge.
- `:154` - a change "returns to the affected earlier unit gate." This names no target set at all.

A second, related defect: `:142` states "All listed edges require human approval." Rewinds live only in the effect column, so their approval requirement is unstated. Because Section 5.3 forbids the machine from *advancing* state but is silent on rewinding, an implementer could reasonably build automatic rewind - which would let a machine change run state without a human decision.

Required correction: enumerate every rewind as a first-class edge in the From/Target columns, and state explicitly whether a rewind is a human-approved transition or a machine-executed invalidation.

## Structural gaps

These do not block the first line of code but will block a coherent schema, a CI verifier, or the pilot.

### 4. The same-UID adversary is unaddressed in the threat model

References: `:404-406`, `:543-545`

Section 22 correctly lists implementing-agent output as adversarial, and places the host-managed append-only store and the configured trust roots inside the v1 trusted computing base. `:545` scopes out only "a fully hostile local operating system."

The realistic attacker in this threat model is a local coding agent running as the same operating-system user as the store - and as whatever key authenticates the exported anchor. Chained records with a per-run head anchor detect truncation and incoherent rewrites. They do not detect a coherent forgery by a process that can rewrite every record and recompute the anchor together. `:404` places the store "outside the worker's writable project tree," which defends against a path-scoped worker but not against a same-UID process.

`:406` concedes that "the exact trust mechanism is an open implementation decision." That single decision is load-bearing for the entire product claim, yet Section 25 lists it as one of eleven bullets alongside "fixture repository design."

Required correction: state the same-UID case explicitly in Section 22 rather than letting the hostile-OS exclusion appear to cover it, and promote the anchor-authentication mechanism to a named prerequisite decision in Section 25.

### 5. Findings have dispositions but no lifecycle states

References: `:106-113`, `:216-231`, `:486-499`

Criteria have a state enum: `PENDING`, `PASSED`, `FAILED`, `WAIVED` (`:108-109`). Findings have only a disposition - `BLOCK`, `WAIVABLE`, `ADVISORY` - which is a classification, not a state.

`:111-113` says an unresolved `WAIVABLE` finding blocks closure "until it is waived, withdrawn, or corrected." Those three resolutions appear in no enum. `:109` ("Only criteria may be `WAIVED`") blocks the obvious reuse of the criterion vocabulary.

JSON Schema work stalls here: there is no field to write a resolved finding into.

Required correction: add a finding lifecycle enum distinct from both the disposition enum and the criterion state enum.

### 6. "Disposition" is overloaded three ways

References: `:108-113`

The same word denotes criterion disposition (`PENDING`/`PASSED`/`FAILED`/`WAIVED`), validator finding disposition (`BLOCK`/`WAIVABLE`/`ADVISORY`), and advisory disposition (`ACCEPT`/`PARK`/`KILL`). Three enums, one name, in six lines of text.

Required correction: rename at least two of the three before schemas freeze.

### 7. Failure identity is undefined

Reference: `:450`

"The same material failure twice ends that route as `FAILED`" is the retry-termination rule and therefore a budget-enforcement primitive. "Material" has no comparison procedure: not exit code, not normalized stderr digest, not failing test identifier.

Section 17 opens by asserting that HMA "applies deterministic rules to classify observed failure evidence." This is the one part of Section 17 that cannot be deterministic as written.

Required correction: define the failure-equality function, and add it to the Section 25 open-decision list, where it currently does not appear.

### 8. The no-shell kernel rule has no ergonomics story

References: `:210`, `:400`

The rule is correct and should be kept: plan-declared commands execute as explicit executable and argument vectors, never through a shell, as an unwaivable kernel rule.

The document never says how a plan unit expresses commands that are conventionally shell-shaped - `make test`, pipelines, globs, `a && b`. Most real verification commands in most real repositories are written that way. The first pilot (Section 24.3) encounters this immediately.

Required correction: state how such commands are represented - an argv vector to the tool itself, a declared multi-step evidence sequence, or an explicit no-shell wrapper contract.

### 9. Risk-floor downgrade is an unenumerated waiver class

References: `:364` versus `:216-224`

Section 13 permits downgrading the deterministic minimum risk floor: "A permitted downgrade must be an explicit waiver." Section 7.2's waivable classes are complexity-budget exceedance, minor performance targets, and non-safety reviewer recommendations. The list is introduced with "such as," so it is not closed - but a risk-floor downgrade is safety-adjacent and materially unlike the three examples.

Required correction: classify risk-floor downgrade explicitly as a waivable class with its own constraints, or move it to the unwaivable kernel in Section 7.1.

### 10. `DRAFT` and `READY_FOR_REVIEW` are orphan vocabulary

Reference: `:106`

Both tokens are defined once and never used again in 622 lines. Verified by grep: one occurrence each, both on the defining line. `APPROVED`, by contrast, appears fifteen times.

Required correction: wire the stage-control states into Section 19's decision surface and Section 5.4's transition rule, or delete them.

## Repository hygiene

- **"HMA" is never expanded.** `:11` implies *human-gated, machine-assisted* but never states the expansion. `README.md:3` gives a tagline, not an expansion. One line in the README resolves it.
- **No `.gitignore`.** Go build artifacts will land in the working tree on the first day of implementation.
- **No LICENSE.** Acknowledged as an open decision at `:620`. Acceptable while the repository is private; blocks publication.
- **Split author identity.** The initial commit is authored as `Ye (Lennon) Li <85519713+lennon-li@users.noreply.github.com>`; both documentation commits are authored as `Lennon Li <yeli@biostats.ai>`. Decide which identity this repository carries before it goes public - the second is a real address that would be permanently in the published history.

## What is holding up well

Recorded so the audit is not read as uniformly negative, and so these properties are preserved through correction.

- README and architecture are consistent with each other. Every claim checked in `README.md` - the detection-based append-only store, the CI and release-approval ordering, the non-goals list, the implementation constraints - matches its section in `docs/architecture.md`. No drift between a summary and its source is unusual at this size.
- The refusal to invent CLI syntax (`:563`) is the right call and is honored throughout. No section pretends an unimplemented command exists.
- The route attestation at `:331-343` carries exactly what CI needs to verify implementer/validator independence - opaque profile digest, provider family, model family, capability classes, permission classes - and nothing host-private. This is the hardest part of Section 13 to get right and it is right.
- Section 25's statement that the document "does not establish that HMA is implemented, installable, secure, or ready for users" is the kind of claim discipline the product is designed to enforce, applied to itself.
