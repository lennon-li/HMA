## Blocking for implementation

These three stop work at the start of implementation, because the deterministic engine cannot be written against them as stated.

### 1. Terminal-outcome derivation is circular

References: `:126-132`, `:450`

`PARTIAL` is defined at `:126-129`. Then `:131` states that `FAILED`, `BLOCKED`, `UNKNOWN`, and `ABORTED` "are derived from the corresponding terminal condition" - which names nothing. Section 17 defines `FAILED` only at route level (`:450`, "ends that route as `FAILED`"), not run level.

A run that stops with three of five criteria passed, one `PERMISSION_OR_SAFETY_BLOCK`, and one `UNKNOWN_FAILURE` is simultaneously `PARTIAL`, `BLOCKED`, and `UNKNOWN` under the current text. Nothing selects between them.

This is blocking because Section 24.1 requires a deterministic engine fixture proving HMA "represents `FAILED`, `BLOCKED`, `UNKNOWN`, `PARTIAL`, and `ABORTED` honestly." That fixture cannot be written without a total ordering.

Required correction: state an explicit precedence function with one predicate per outcome - for example `ABORTED` > `BLOCKED` > `UNKNOWN` > `FAILED` > `PARTIAL` > `VERIFIED_WITH_WAIVERS` > `VERIFIED_SUCCESS` - and define the exact condition that makes each predicate true.

### 2. The approval-binding contract contradicts itself

References: `:164-182`

`:164` states every approval is "universally bound to" a thirteen-field list. That list includes accepted plan digest (`:173`), plan-declared required evidence digest set (`:174`), and active waiver-operation digest set (`:175`). None of those exist at the Grounding to Acceptance criteria transition.

`:179-181` patches exactly one case, exempting produced head and diff for early transitions. `:182` then changes doctrine without saying so: "A packet becomes stale only when a field it actually binds changes."

Which fields a given stage actually binds is never stated anywhere in the document. Section 21 requires CI to "reject approvals made stale by later changes," which CI cannot do without that mapping.

Required correction: replace the universal list with a per-stage binding matrix - rows are the nine stage transitions, columns are the binding fields, cells are bound or not bound. CI and the local gate both read that one table.

### 3. "No unlisted edge is legal" is violated by its own table

References: `:145-159`

`:159` states "No unlisted edge is legal." The invalidation-effect column of the same table requires transitions the From/Target columns never enumerate:

- `:148` - a criteria or non-goal change "rewinds to Acceptance criteria." No row permits Planning, Route selection, Implementation authorization, Implementation review, Verification, or Independent validation to reach Acceptance criteria. Only `:156` (Release and closure) and `:157` (which allows Grounding, Planning, or terminal only) offer rewind targets.
- `:153` - a produced head or diff change "returns to Implementation authorization or review." There is no Verification to Implementation authorization edge and no Verification to Implementation review edge.
- `:154` - a change "returns to the affected earlier unit gate." This names no target set at all.

A second, related defect: `:142` states "All listed edges require human approval." Rewinds live only in the effect column, so their approval requirement is unstated. Because Section 5.3 forbids the machine from *advancing* state but is silent on rewinding, an implementer could reasonably build automatic rewind - which would let a machine change run state without a human decision.

Required correction: enumerate every rewind as a first-class edge in the From/Target columns, and state explicitly whether a rewind is a human-approved transition or a machine-executed invalidation.

## Structural gaps

These do not block the first line of code but will block a coherent schema, a CI verifier, or the pilot.

### 4. The same-UID adversary is unaddressed in the threat model

References: `:404-406`, `:543-545`

Section 22 correctly lists implementing-agent output as adversarial, and places the host-managed append-only store and the configured trust roots inside the v1 trusted computing base. `:545` scopes out only "a fully hostile local operating system."

The realistic attacker in this threat model is a local coding agent running as the same operating-system user as the store - and as whatever key authenticates the exported anchor. Chained records with a per-run head anchor detect truncation and incoherent rewrites. They do not detect a coherent forgery by a process that can rewrite every record and recompute the anchor together. `:404` places the store "outside the worker's writable project tree," which defends against a path-scoped worker but not against a same-UID process.

`:406` concedes that "the exact trust mechanism is an open implementation decision." That single decision is load-bearing for the entire product claim, yet Section 25 lists it as one of eleven bullets alongside "fixture repository design."

Required correction: state the same-UID case explicitly in Section 22 rather than letting the hostile-OS exclusion appear to cover it, and promote the anchor-authentication mechanism to a named prerequisite decision in Section 25.

### 5. Findings have dispositions but no lifecycle states

References: `:106-113`, `:216-231`, `:486-499`

Criteria have a state enum: `PENDING`, `PASSED`, `FAILED`, `WAIVED` (`:108-109`). Findings have only a disposition - `BLOCK`, `WAIVABLE`, `ADVISORY` - which is a classification, not a state.

`:111-113` says an unresolved `WAIVABLE` finding blocks closure "until it is waived, withdrawn, or corrected." Those three resolutions appear in no enum. `:109` ("Only criteria may be `WAIVED`") blocks the obvious reuse of the criterion vocabulary.

JSON Schema work stalls here: there is no field to write a resolved finding into.

Required correction: add a finding lifecycle enum distinct from both the disposition enum and the criterion state enum, for example `OPEN`, `RESOLVED`, `WAIVED`, and `WITHDRAWN`, with exact closure semantics.

### 6. "Disposition" is overloaded three ways

References: `:108-113`

The same word denotes criterion disposition (`PENDING`/`PASSED`/`FAILED`/`WAIVED`), validator finding disposition (`BLOCK`/`WAIVABLE`/`ADVISORY`), and advisory disposition (`ACCEPT`/`PARK`/`KILL`). Three enums, one name, in six lines of text.

Required correction: rename at least two of the three before schemas freeze.

### 7. Failure identity is undefined

Reference: `:450`

"The same material failure twice ends that route as `FAILED`" is the retry-termination rule and therefore a budget-enforcement primitive. "Material" has no comparison procedure: not exit code, not normalized stderr digest, not failing test identifier.

Section 17 opens by asserting that HMA "applies deterministic rules to classify observed failure evidence." This is the one part of Section 17 that cannot be deterministic as written.

Required correction: define a failure-equality function and add it to the Section 25 open-decision list. A practical identity should be derived from stable machine evidence such as check identifier, exit status, and a normalized failure signature rather than agent prose.

### 8. The no-shell kernel rule has no ergonomics story

References: `:210`, `:400`

The rule is correct and should be kept: plan-declared commands execute as explicit executable and argument vectors, never through a shell, as an unwaivable kernel rule.

The document never says how a plan unit expresses commands that are conventionally shell-shaped - `make test`, pipelines, globs, `a && b`. Most real verification commands in most real repositories are written that way. The first pilot (Section 24.3) encounters this immediately.

Required correction: state how such commands are represented - an argv vector to the tool itself, a declared multi-step evidence sequence, or an explicit no-shell wrapper contract.

### 9. Risk-floor downgrade is an unenumerated waiver class

References: `:364` versus `:216-224`

Section 13 permits downgrading the deterministic minimum risk floor: "A permitted downgrade must be an explicit waiver." Section 7.2's waivable classes are complexity-budget exceedance, minor performance targets, and non-safety reviewer recommendations. The list is introduced with "such as," so it is not closed - but a risk-floor downgrade is safety-adjacent and materially unlike the three examples.

Required correction: classify risk-floor downgrade explicitly as a waivable class with its own constraints, or move it to the unwaivable kernel in Section 7.1.

### 10. `DRAFT` and `READY_FOR_REVIEW` are orphan vocabulary

Reference: `:106`

Both tokens are defined once and never used again in 622 lines. Verified by grep: one occurrence each, both on the defining line. `APPROVED`, by contrast, appears fifteen times.

Required correction: wire the stage-control states into Section 19's decision surface and Section 5.4's transition rule, or delete them.

## Second-pass workflow-harness audit

The first audit concentrated on internal consistency. This pass asks a narrower product question: if a worker returns code and evidence, has HMA specified enough deterministic machinery to answer "is this unit done; if not, why; and what happens next?"

The answer is not yet. The architecture contains nearly all of the ingredients, but the executable harness semantics are spread across criteria, plan units, evidence, failure routing, closure, CI, and human transition rules rather than defined as one canonical evaluation contract.

### 12. No canonical harness-evaluator contract exists

References: Sections 5, 17, 18, 20, 21, and 24.1.

The architecture names a "deterministic transition engine" and requires deterministic fixtures, truthful outcomes, and exactly one next action. It never defines the canonical input/output contract of the decision function that all of those behaviors depend on.

As written, an implementer must independently infer whether the central operation is a transition evaluator, closure evaluator, criterion evaluator, CI verifier, or a composition of all four. That invites semantic drift between local gating and CI even though Section 23 requires the same binary for both.

For a workflow harness, the product needs one normative operation conceptually equivalent to:

```text
evaluate(contract, evidence, state, policy)
  -> verdict
  -> reasons
  -> criterion_results
  -> failure_class
  -> next_action
  -> authority_required
```

The exact Go API and CLI syntax can remain deferred. The semantic function cannot.

Required correction: define a canonical deterministic evaluator contract before package or CLI design. Every gate, CI verification, terminal report, and fixture should consume or test that same decision model rather than reimplementing outcome logic separately.

### 13. Criteria and evidence lack deterministic satisfaction predicates

References: Sections 9, 10, 14, 20, 21.

Section 9 requires "measurable" acceptance criteria. Section 10 records verification commands and required evidence. Section 14 captures command execution. Section 21 says CI must rerun required checks and "map results to approved criteria." None of those sections states how a criterion becomes `PASSED` or `FAILED` from machine evidence.

A command's exit code is not universally equivalent to criterion truth. Some criteria may depend on a value in structured output, a changed-file invariant, a diff budget, several checks together, or the absence of a condition. Without a declared predicate, the mapping from evidence to criterion state can fall back to agent or validator interpretation, violating the intended deterministic harness boundary.

Required correction: each machine-verifiable criterion must carry or reference an explicit satisfaction rule. At minimum the contract must define the evidence IDs used, the deterministic predicate over their normalized fields, and the result produced for missing or indeterminate evidence. Semantic-only criteria must be explicitly typed as requiring independent validation rather than pretending to be deterministic.

### 14. Human approval is coupled to every state transition

References: Sections 5.3, 5.4, 10, 17.

This is a design risk, not a contradiction. The architecture intentionally says every transition requires a fresh human decision. However, it currently treats authority-changing actions and machine-observed facts through the same transition concept.

That means ordinary harness observations such as "required test failed," "evidence is stale," "scope drift detected," or "criterion remains failed" can force a human gate merely to record reality or follow a pre-approved failure route. This risks turning HMA into a human-driven state machine and encouraging reflexive approvals - one of the failure modes the product explicitly wants to avoid.

Required design decision: separate at least two concepts:

1. **machine-recorded evaluation/invalidation** - HMA may record evidence-derived state truth and invalidate stale downstream packets without gaining authority; and
2. **authority-changing transition** - human approval remains mandatory when criteria, scope, permissions, route/escalation, waivers, destructive/external effects, or release authority changes.

If the product deliberately retains human approval for every factual state change, state that as an accepted usability cost and add a fixture proving that repeated failure handling cannot devolve into meaningless click-through approvals.

### 15. The executable harness contract is distributed rather than first-class

References: Sections 9, 10, 17, 18, and 20.

A plan unit already contains much of a harness: observable behavior, criteria advanced, scope boundaries, expected failure, verification commands, budgets, retry/escalation conditions, and non-goals. But completion conditions, failure routing, finding resolution, and outcome derivation live in other sections and are not assembled into one versioned, digest-bound unit that can be evaluated independently.

The result is that "what done means" is implicit in the combination of several record types and global prose. That makes portable fixtures harder and weakens the claim that a plan unit is the smallest independently verifiable behavioral increment.

Required correction: make a first-class per-unit **harness contract** (the final product name may differ) that references the approved criteria, deterministic predicates, evidence requirements, scope/budgets, failure routes, validator requirement, closure rules, and applicable policy digest. It should be immutable after approval; a material change creates a new digest and invalidates dependent approvals.

This does not require a new framework. It may be a normalized projection of existing records rather than another source of truth.

### 16. MVP fixtures lack an end-to-end decision-table contract

Reference: Section 24.1.

The deterministic fixture list is strong but feature-oriented: stale grounding, route proposal, scope drift, outcome representation, waivers, tampering, reruns, and next actions are listed as separate behaviors. There is no normative table proving that a fixed input state produces one and only one verdict and next action across conflicting conditions.

This matters because several current defects are interaction defects, not isolated-feature defects. For example: partial criterion success plus a safety block plus unknown evidence must have one outcome; stale evidence plus a correctable failure must have one next action; an unresolved waivable finding plus otherwise passing criteria must have one closure result.

Required correction: add table-driven conformance fixtures whose rows bind at least:

- criterion states;
- evidence freshness/integrity;
- finding states;
- failure class and retry count;
- scope/budget drift;
- active waivers;
- authority/permission state;
- expected verdict;
- expected single next action;
- whether fresh human authority is required.

These fixtures should be executable against the same canonical evaluator locally and in CI.

## What is holding up well

Recorded so the audit is not read as uniformly negative, and so these properties are preserved through correction.

- README and architecture are consistent with each other. Every claim checked in `README.md` - the detection-based append-only store, the CI and release-approval ordering, the non-goals list, the implementation constraints - matches its section in `docs/architecture.md`.
- The plan-unit contract already contains most of the raw material needed for a useful workflow harness: bounded observable change, approved scope, verification commands, budgets, retry/escalation conditions, and non-goals. The correction is primarily to make its evaluation semantics explicit and canonical, not to replace it.
- Failure routing is directionally strong: transient, correctable, capability mismatch, validation, permission/safety, and unknown failures are treated differently; blind third attempts are forbidden.
- The refusal to invent CLI syntax is the right call and is honored throughout. Defining the semantic evaluator does not require prematurely defining command names.
- The route attestation carries what CI needs to verify implementer/validator independence - opaque profile digest, provider family, model family, capability classes, permission classes - without host-private configuration.
- Section 25's statement that the document does not establish that HMA is implemented, installable, secure, or ready for users applies the product's own claim discipline to itself.

## Recommended order of correction

1. **Before any Go implementation:** fix Findings 1, 2, and 3, then define Findings 12 and 13. These determine the deterministic evaluator's core semantics.
2. **Before JSON Schema freezes:** fix Findings 5, 6, and 15 so criterion, finding, and harness-contract records have unambiguous lifecycles and one canonical evaluation boundary.
3. **Make the human-gate decision explicitly:** resolve Finding 14 before implementing transition execution. Prefer separating machine-observed evaluation/invalidation from changes in authority while preserving human approval for criteria, scope, permissions, escalation, waivers, external effects, and release.
4. **Before the deterministic engine is called complete:** implement Finding 16's table-driven conformance fixtures, including combinations of competing terminal conditions and next actions.
5. **Before persistence/security claims:** resolve Finding 4 and choose the anchor-authentication mechanism under an explicit same-UID threat assumption.
6. **During implementation planning:** resolve Findings 7, 8, 9, and 10.
7. **Repository hygiene:** add `.gitignore` with the first code commit; resolve naming, license, and author-identity questions before publication.

## Recommended implementation nucleus

Do not start with the full CLI surface. The first executable milestone should be a pure deterministic evaluator over recorded fixtures:

```text
Task request
  -> approved harness contract
  -> synthetic/fresh evidence
  -> evaluator
  -> verdict + reasons + exactly one next action + authority requirement
```

The minimum success condition for that milestone is not "the CLI runs." It is: for every conformance-table row, HMA produces the one specified truthful verdict and next action without consulting agent confidence or prose.
